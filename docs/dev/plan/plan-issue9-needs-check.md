# 実装計画: 「要確認」の印を付けられるようにする (Issue #9)

## 目的

問題の中身に疑問があったとき、その問題に「要確認」の印と理由のメモを付けておけるようにする。
あとで解いたときに印と理由が見えるので、疑問を忘れずに確かめられる。

- 疑問の出どころは問わない (AI 精査で裏取りできなかった、解いていて気になった、など)
- 「未確認」(`is_reviewed`) とは別のものにする
  - 「未確認」は、人がまだ一度も確認していないという状態
  - 「要確認」は、確かめたい疑問があるという印。確認済みの問題にも付けられる
  - 2 つは連動させない。「確認済みにする」を押しても、要確認の印は外れない

## 今回やること・やらないこと

やること:

- DB に印と理由の列を足す
- 印と理由を変える API
- クイズ画面: 印の表示、理由の表示 (解いたあと)、印の付け外し
- エディタ: 印と理由の編集
- 「要確認」の問題だけを出題するモード
  - Issue の「『要確認』の問題だけを一覧で見られるようにする」は、一覧の代わりにこのモードで満たす
  - 確かめる流れが「解く → 理由を見る → 直す・外す」の 1 つにそろい、印を外せばモードから消えるため
- 「未確認」の問題だけを出題するモード (Issue の範囲外。Issue #6 の計画書の「決めていないこと」に残っていたものを、ここで扱う)
  - 要確認のモードと同じ場所 (API のモード・クイズ画面のモード選びのカード・`MODE_LABEL`) を触るので、まとめて作る
  - AI 精査のあとに未確認で入れた問題を、アプリで確かめていくために使う

やらないこと (必要になったら別 Issue にする):

- 一覧の画面、ダッシュボードの件数
- JSON に項目を足し、インポートで印を付けて入れること (Issue でも任意)

## 1. DB に列を足す

対象: [db.py](../../../db.py) の `init_db()`

- `questions` に 2 つの列を足す
  - `needs_check INTEGER NOT NULL DEFAULT 0`: 要確認の印 (0 = なし、1 = あり)
  - `check_note TEXT`: 理由のメモ (なければ `NULL`)
- `CREATE TABLE IF NOT EXISTS questions` の定義にも足す (新規 DB 用)
- 既存 DB には、`PRAGMA table_info(questions)` にないときだけ `ALTER TABLE ... ADD COLUMN` する
  - `history` の移行と同じ書き方でよい
  - `is_reviewed` のときと違い、既存の行の値を書き換えない (全部「印なし」でよい)。そのため、トランザクションで囲む必要はない
  - 2 つの列は別々に「なければ足す」を確かめる。Python の sqlite3 では ALTER がその場で確定するので、途中で落ちても次の起動で残りが足される
- 印を外したとき、理由のメモは消さずに残す
  - 付け直したときに前の理由が見えるほうが便利なため
  - 画面では、印がないときは理由を出さない

### インポートとの関係

[converter/import_json.py](../../../converter/import_json.py) は、未確認の問題を上書きするとき、列を指定した `UPDATE` を使っている。
`needs_check` と `check_note` は `UPDATE` の対象に入れないので、再インポートしても印と理由は消えない。
これはテストで押さえる。

## 2. API

対象: [routers/questions.py](../../../routers/questions.py)

- GET (`/api/questions`、`/api/questions/{id}`): どのモードも `SELECT q.*` で取っているので、2 つの列はそのまま返る (コードで確かめた。テストでも押さえる)
  - `needs_check` は 0 / 1 の整数で返る (`_parse_question()` は変換しない)
- 理由の整形と型の確かめは、関数にまとめて PATCH・PUT・POST の 3 つで使う
  - `_normalize_check_note()`: 前後の空白を取り、空になったら `NULL` にする
  - `_check_needs_check()`: 本文に `needs_check` があれば真偽値か、`check_note` があれば文字列か `null` かを確かめ、違えば 422 (`_check_is_reviewed()` と同じ形)
- 印と理由だけを変える API を足す
  - `PATCH /api/questions/{id}/check`、本文は `{"needs_check": true, "check_note": "…"}`
  - `needs_check` は必須で、`StrictBool` で受ける (`1` や `"true"` は 422)
  - `check_note` は `Optional[StrictStr] = None` で受け、`model_fields_set` で「省略」と「`null` の明示」を分ける
    - 省略したとき: 今の値を保つ
    - `null` を明示したとき: 理由を消す
    - 数値などは 422
  - 存在しない ID は 404
  - 返す値は、整形したあとの `needs_check`・`check_note`。クイズ画面は、この値で手元の問題データを書き換える
  - クイズ画面のボタンから使う
- 出題モードを足す: `GET /api/questions?mode=needs_check`
  - `needs_check = 1` の問題を、回・問題番号の順に返す
  - ほかの条件 (科目・回・件数) は使わない。`question_type`・`multiple_only` の絞り込みは、ほかのモードと同じく効かせる
  - `get_questions()` の docstring のモードの説明にも足す
- 同じ形で、`GET /api/questions?mode=unreviewed` も足す
  - `is_reviewed = 0` の問題を、回・問題番号の順に返す
  - 条件の扱いは `needs_check` と同じ
- 2 つのモードは別々に置く。「未確認 または 要確認」をまとめて出すモードは作らない
- PUT (`/api/questions/{id}`): 本文に `needs_check`・`check_note` があるときだけ、それぞれ更新する
  - `is_reviewed` と同じく、古い画面からの保存で印が消えないように
- POST (`/api/questions`): 本文の値を整形して入れる。送られなければ列の既定値 (印なし・理由なし)

## 3. クイズ画面

対象: [static/js/quiz.js](../../../static/js/quiz.js)、[static/quiz.html](../../../static/quiz.html)、[static/css/style.css](../../../static/css/style.css)

### 表示

- 印のある問題には、バッジ列に「⚠️ 要確認」バッジを出す (`renderQuestion()`)
  - 「未確認」の `<span id="q-review-badge">` は `renderReviewBadge()` が中身を丸ごと書き換えるので、隣に別の `<span id="q-check-badge">` を足す
  - バッジは解く前から出す
- 理由は、解いたあとの解説欄にだけ出す
  - 理由には「正答は 3 ではないか」のように答えに触れる内容が入りうるので、解く前には見せない
  - `quiz.html` の `#fb-answer` と `#fb-explanation` の間に、理由の枠の要素を足す
    - `#fb-explanation` は解説が無いと隠れるので、その中には入れない
  - 目立つ枠で「⚠️ 要確認: (理由)」と出す。理由が空なら「⚠️ 要確認」だけ
  - 理由は `textContent` で入れる (`innerHTML` で差し込むと、`<` などが HTML として解釈されるため)
  - 枠には `white-space: pre-wrap` を付ける (エディタで複数行の理由を書けるため)
  - `judgeAnswer()` で毎回描き直す (前の問題の枠を残さないため)

### 付け外し

- 解説欄のボタン列 (`fb-actions`) に、ボタンを 1 つ足す
  - 印がないとき: 「⚠️ 要確認にする」。押すと理由を聞き (`prompt()`)、`PATCH` を呼ぶ
    - キャンセルしたら何もしない
    - 前の理由が残っているときは、それを初期値にせず、「空のまま OK なら前の理由を使う」と添えて聞く
      - `prompt()` の入力欄は 1 行なので、複数行の理由を初期値にすると改行が落ちるおそれがある
      - 空のまま OK なら、`check_note` を省略して送る (前の理由が保たれる)
    - 前の理由がないときに空のまま OK なら、理由なしで印を付ける
  - 印があるとき: 「要確認を外す」。押すと `PATCH` で印だけを外す (理由は残す)
- 押したら、手元の問題データを書き換え、バッジ・理由の枠・ボタン列だけを描き直す
  - `renderQuestion()` は呼ばない (解答の状態が戻り、解答履歴が二重に記録されるため。`updateQuestionReviewStatus()` と同じ理由)

### 出題モード

- クイズ画面のモード選び (`quiz.html` の `.mode-grid`) に、モードのカードを 2 枚足す
  - 「⚠️ 要確認の問題」「印を付けた問題を確かめる」
  - 「🔍 未確認の問題」「まだ人が確認していない問題を確かめる」
  - 以下は 2 つのモードで共通
- 「間違えた問題のみ」と同じく、科目・件数・回の設定は出さない (`updateSetupOptions()`)
  - 代わりに、説明の 1 行 (`info-wrong` と同じ形) を出す
- 対象が 0 問のときは、ほかのモードと同じく「対象の問題が見つかりませんでした」を出す
- 解答履歴と正答率には、ほかのモードと同じく記録する
  - 確かめるために解いた結果も、学習の記録として残したいため
- セッションの `mode` には `needs_check`・`unreviewed` が入る
  - ダッシュボードのセッション一覧は、`static/js/dashboard.js` の `MODE_LABEL` でモードの名前を出しているので、「要確認」「未確認」を足す
  - `routers/sessions.py` の `mode` のコメント (モードの一覧) にも足す

### エディタからの反映

- 今の `updateQuestionReviewStatus(id, isReviewed)` は名前を変えずに、要確認の 2 項目を受け取る引数を足す
  - 例: `updateQuestionReviewStatus(id, isReviewed, { needs_check, check_note })`。3 つ目が無ければ要確認は変えない
  - 名前を変えると、更新前に開いたクイズのタブで、エディタからの反映が黙って止まるため (`notifyOpener()` は関数があるかを確かめてから呼ぶ)
  - 描き直すのは、表示中の問題のときだけ。理由の枠とボタン列は、解答済み (`state.answered`) のときだけ描き直す (今と同じ条件)
  - エディタの `notifyOpener()` も、要確認の 2 項目を渡すようにする
- 問題文・解説など、中身の表示を新しくする仕組みは、今回も入れない (#7 で扱う)
